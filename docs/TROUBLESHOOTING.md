# 排障

## 先确认当前场次和构建

读取 `results/` 中对应日期与场次的独立文件，看 `build`、`session`、`generatedAt`、`verdict`。`result.json` 是最新一场，不一定是正在调查的那场。日志可能稍后写盘，单次没有新日志不等于引擎死亡。

## 常见情况

| 现象 | 首先核对 | 不应直接推断 |
|---|---|---|
| 没有进入活动页 | 实时前台包名、`entry-status.json`、当前入口坐标、系统对话框 | 所有入口坐标都坏了 |
| 一直停在桌面或打开方式选择器 | Launcher是否存在、启动后前台是否真变化 | 启动API返回即成功 |
| 进程存在但不出手 | 实际守候引擎、心跳是否连续推进、当前场次与自动启动标记 | 进程存在就代表守候还活着 |
| 提示锁场失败 | 场次条、按钮文案、倒计时格与目标时间 | 任意“立即抢”都对应当前场次 |
| 按钮一直“立即抢” | 触控数、正在抢采样、页面失败提示、对应独立结果 | 脚本肯定没点，或一定已售罄 |
| 显示活动太火爆 | 完整提示和实际响应证据（如果有） | 一定被风控或一定只是网慢 |
| 有大量触控却没领到 | H5是否处理、业务结果、资格与库存证据 | 加快点击必定改善 |
| 页面显示成功 | 核验券包里同一张目标券是否到账 | 通用“恭喜”文字等于到账 |

## 结果字段

- `fireCount`：标为领取动作的触控API调用数，排除入口、选场和关闭弹窗操作。
- `gestureAccepted`：其中API返回成功的数量，不是平台成功领取次数。
- `uiFeedback.samples`：按钮状态变更采样；`observedAt` 是完成读取的时间。
- `uiFeedback.messages`：读到的瞬时页面提示，可能有遗漏。
- `pageEvidence.status`：对前端证据的分类，不是后端错误码。
- `not_in_page`：进场失败，未执行领取。
- `wrong_session` / `precheck_failed`：场次或前置验证失败。
- `gesture_failed` / `lost_page`：手势失败或执行过程中丢失目标页面。
- `fired_no_confirm`：执行了触控，没有成功确认。
- `serviceErrorCode:null` / `causeConfirmed:false`：尚未取得真实接口错误码、尚未确定根因。

## 建议的排查顺序

先分辨未进场、未触控、已触控但业务未确认三个阶段。只对已证实的代码问题修改一个变量，并用回归保护。页面改版先校准页面；引擎消失先查生命周期；业务失败先保留真实失败证据。

公开反馈时提供脱敏的场次概要和可复现步骤。不要提交Cookie、Token、账号页面、原始全量日志或ADB序列号。
