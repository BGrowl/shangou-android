# 实测与证据边界

本页是人工整理的脱敏摘要；公开仓库不包含原始设备日志。数据用于说明已观察到的行为，不用于宣称领取成功。

## 进场与生命周期

2026-10-19上午，三场进场失败，前台记录为华为系统界面。系统事件显示 `HwResolverActivity`；旧代码仍按运营弹窗坐标尝试关闭。随后系统以 `recent-task-trimmed` 销毁AutoX控制Activity，原守候引擎消失，而脚本进程还存在。

v7改用明确Launcher组件、实时窗口守卫和独立非UI执行器。手机验证结果：

| 检查 | 观察 |
|---|---|
| 从桌面进入活动页 | 22.173秒，页面显示14:00开抢 |
| App完全退出后的冷启动 | 38.402秒，页面显示14:00开抢 |
| 桌面执行关闭弹窗路径 | 0次触控 |
| 控制Activity销毁后 | 独立执行器存在，心跳继续更新 |
| v7.1本地回归 | 63/63通过 |

两次进场验证使用v7.0；v7.1只补充控制页在执行器消失后的状态恢复，另做了完整回归和手机运行核验。上述进场检查没有点击领取按钮。

## 哪些结论可以成立

- 四场实际进入了触控流程，上午的进场失败在这些场次中没有重现。
- 本地触控API正常返回，页面曾出现处理状态，最终没有记录到成功确认。
- 后两场观察到了“活动太火爆了，请稍后再试”。

## 哪些结论还不能成立

- 279次触控不等于279次H5事件，更不等于279次领取请求。
- “正在抢”不证明服务端已接受领取；它也可能覆盖前端参数准备阶段。
- “活动太火爆”不能单独区分拥堵、库存或账号限制。
- 公共时间源的低RTT不能证明领取服务端开抢误差为零。
- 所有场次的 `serviceErrorCode` 仍为空，不能填写推断出的风控码。
- 未核验到同一张目标券实际到账；不存在已证实的抢券成功率。

观察线程大约在整点后10秒结束，之后到最终按钮复查之间存在瞬时提示遗漏空档。应把它作为诊断质量问题调查，不能把它当成已经证实的领取失败根因。
